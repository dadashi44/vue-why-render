## [0.3.0] — 2026-10-02

### Добавлено

- Проверки рендеров в тестах — отдельный вход `vue-why-render/test`. `expectRenders(ProductCard).toBe(0, action)` падает, если компонент перерисовался, и в сообщении называет причину: `prop badge: { text } -> { text } (new reference, same value)`. Лишний рендер, починенный однажды, перестаёт возвращаться.
- `renderTracking()` — Vue-плагин для `global.plugins` в `mount()`. Именно плагин: test-utils создаёт приложение сам и наружу его не отдаёт. В тестовом режиме панель и оверлей выключены, чтобы не трогать разметку, по которой тест ищет элементы, а монтирования не считаются — первый рендер лишним не бывает.
- `recordRenders(action)` отдаёт сырые события окна, `toBeAtMost()` — для случаев, где точное число хрупко, `stopRenderTracking()` снимает слежение в `afterEach`.

- Подсказки: рядом с причиной панель пишет, что с ней делать. Три шаблона, все по данным рантайма — пересобранный в родителе объект, обработчик, создаваемый заново, и рендер, пришедший от родителя при неизменных пропах (кандидат на `v-memo`). Формулировки осторожные: пакет знает, что пропс пришёл новой ссылкой, но не знает откуда, а подсказка-диагноз хуже её отсутствия.
- Подсказка молчит там, где вывод нельзя сделать честно: при `trackProps: false` или `trackReasons: false` «ничего не менялось» означало бы «мы не смотрели», а компонент, который только смонтировался, не получает советов вовсе — мемоизировать то, что ни разу не обновлялось, вредно.
- `ComponentRecord.updateCount` — сколько рендеров были обновлениями, а не монтированием. Без этого счётчика подсказка про `v-memo` цеплялась к компонентам с единственным рендером-монтированием.
- Подсказки попадают в отчёт: `ReportComponent.hints`.
- `hintsFor()` и `hintsForRecord()` в публичном API — можно строить свои отчёты поверх тех же выводов.

- Вердикт «новая функция на каждый рендер» для пропов-функций. Две стрелки не равны никогда, поэтому `referenceOnly` для них всегда `false` — и в панели были видны две одинаковые строки `ƒ onPick() → ƒ onPick()` без единого слова о том, почему это считается изменением.
- Отчёты: `getReport()` отдаёт всю сессию одним сериализуемым объектом, `saveReport()` скачивает его файлом, в панели для этого появилась кнопка «отчёт». В файл кладутся версии пакета и Vue, URL, длительность сессии и опции сканера — без них чужой отчёт нечитаем: непонятно, то ли компонент не перерисовывался, то ли его отфильтровали.
- Компоненты в отчёте агрегируются по ключу `file::name`. `uid` живёт одну сессию и между отчётами бессмыслен, поэтому несколько инстансов одного компонента сводятся в один агрегат.
- `parseReport()` проверяет чужой файл и отказывается читать формат новее поддерживаемого. Отчёт приходит из чужих рук, и тихо проглоченный мусор превратился бы в неверные выводы о чужом приложении.
- `diffReports(before, after)` и `formatDiff()` — сравнение двух отчётов. Показывает, что починилось, что не тронуто и что сломалось по дороге; регрессии идут первыми. Если сессии несопоставимы — разной длительности, с разными `include`/`exclude`, `includeMounts` или `minDuration` — дифф говорит об этом в `warnings`, а `formatDiff` печатает их раньше чисел.

### Исправлено

- Модуль объявлял совместимость с Nuxt `>=3.0.0`, хотя пакету нужен Vue `^3.3.0`. Nuxt тянет Vue прямой зависимостью, и до 3.5.0 там приколочен `^3.2.x` — на ранних Nuxt 3 с зафиксированным локом установка упиралась бы в peer-конфликт. Граница поднята до `>=3.5.0`.

## [0.2.0] — 2026-10-01

### Добавлено

- Nuxt-модуль: `modules: ['vue-why-render/nuxt']`. Регистрирует клиентский плагин сам и только в деве — в прод-сборке не остаётся ни вызова, ни импорта. Раньше это надо было помнить руками: суффикс `.client.ts` и проверка `import.meta.dev`, два источника тикетов «не работает».
- Опции читаются из ключа `whyRender` в `nuxt.config`. Переносятся в сгенерированный плагин кодом, а не через `runtimeConfig`: JSON превращает регулярки в пустой объект, и фильтры `include`/`exclude` молча переставали работать. Функции перенести нельзя — модуль отбрасывает их и называет в терминале каждую поимённо.
- Подпуть `vue-why-render/nuxt` в `exports`. `@nuxt/kit` объявлен опциональным peer-зависимостью: он приезжает вместе с самим Nuxt, у пакета по-прежнему ноль обязательных зависимостей.

## [0.1.8] — 2026-09-21

### Исправлено

- Клик по строке в панели молчал, если дев-сервер отдавал эндпоинт по другому пути. Теперь пакет перебирает кандидатов: сначала настроенный `openInEditorUrl`, потом вайтовский `/__open-in-editor`, потом нукстовский `/__nuxt_devtools__/open-in-editor`. Nuxt-проектам больше не нужно настраивать путь руками.
- Ответ дев-сервера больше не проглатывается молча. Если открыть файл не удалось ни по одному пути, панель один раз за сессию пишет в консоль, что делать — с переменной `LAUNCH_EDITOR` и списком редакторов.

### Добавлено

- Раздел про открытие файлов в редакторе во всех трёх README: почему `launch-editor` по умолчанию зовёт `code`, откуда берётся `ENOENT` и как назвать свой редактор явно.

## [0.1.6] — 2026-09-21

### Добавлено

- Опция `locale`: язык панели и подписей причин — `en`, `ru` или `zh-CN`. По умолчанию английский. Словарь лежит обычным объектом, зависимостей не добавилось.
- README на английском (основной), плюс переводы на русский и китайский, и демо-гифка в первом экране.

- Сообщение о сбое в `console.warn` теперь всегда на английском: это диагностика для разработчика, а не часть интерфейса.
- Ссылки в README абсолютные — на странице npm README рендерится вне репозитория, и относительные пути там не разрешались.

## [0.1.5] — 2026-09-21

### Изменено

- Релизы уезжают в npm через доверенную публикацию (OIDC): токена в секретах репозитория больше нет, npm выдаёт одноразовые права по OIDC-токену GitHub Actions и сам проставляет провенанс. Заодно убрана ветка «секрета нет — публикацию пропускаем», из-за которой четыре релиза подряд молча не доезжали до реестра.
- Версии GitHub Actions подняты до актуальных: старые собраны под Node.js 20 и уже запускались на 24 принудительно.

### Добавлено

- Сайт проекта с живой песочницей: <https://dadashi44.github.io/vue-why-render/>. Панель на нём настоящая и сканирует демо-компоненты прямо на странице.

## [0.1.4] — 2026-09-17

### Исправлено

- `esbuild` и `@eslint/js` объявлены в `devDependencies`. Постобработка бандла импортирует `esbuild`, а `eslint.config.js` — `@eslint/js`, но оба приезжали транзитивно через `vite` и `eslint`. npm, yarn с `nodeLinker: node-modules` и bun поднимают их в корень `node_modules`, поэтому сборка проходила; pnpm даёт доступ только к прямым зависимостям, и `pnpm run build` падал с `ERR_MODULE_NOT_FOUND`. На публикуемый бандл не влияет — правка только для сборки и линта.

## [0.1.3] — 2026-09-16

### Исправлено

- Публикуемый бандл больше не ломает прод-сборку приложения. Плагины, переписывающие код у потребителя (`@rollup/plugin-commonjs` в составе Vite), считают смещения в байтах: кириллица в комментариях и строках сдвигала их, вставки уезжали, и сборка Nuxt падала с `Unexpected token &&` внутри нашего файла. Теперь бандл проходит постобработку — комментарии вырезаются, не-ASCII уходит в `\uXXXX`. Проверено на живом проекте: до — падало, после — собирается, и пакет в прод-бандл не попадает.

### Изменено

- Определение режима сборки убрано полностью: даже `globalThis.process` в бандле включал тот же механизм переписывания. Сканер включён по умолчанию, гасить его в проде должен вызывающий код статическим флагом (`import.meta.dev`, `import.meta.env.DEV`) — тогда вырезается и импорт пакета.
- Сорсмапы к публикуемому бандлу больше не выкладываются.

## [0.1.2] — 2026-09-16

### Исправлено

- Пакет ломал прод-сборку приложения. Единственная голая ссылка на `process.env.NODE_ENV` заставляла `@rollup/plugin-commonjs` считать наш ESM-бандл смешанным CommonJS, и его переписывание выдавало синтаксически битый код — сборка Nuxt падала с `Unexpected token &&` внутри нашего файла. Теперь режим читается через `globalThis.process`, голой ссылки в бандле нет.

### Изменено

- Сканер по умолчанию включён везде, кроме явно опознанного прода. В браузерном бандле `process` недоступен, поэтому угадать режим оттуда нельзя — гасить сканер в проде должен вызывающий код (`if (!import.meta.dev) return` в Nuxt, см. README).
- Убрано предупреждение в консоль про неопределённый режим: определять больше нечего.

## [0.1.1] — 2026-09-16

### Исправлено

- Сбор причин ронял приложение, которое сканируешь: поиск имени рефа перечислял `setupState` и тем самым вычислял computed'ы приложения прямо внутри `renderTriggered`. Найдено прогоном на реальном проекте — падала гидрация. Теперь свойства читаются через дескрипторы, геттеры не трогаются.
- Ошибка внутри хуков сканера больше не всплывает как ошибка рендера чужого компонента: хуки обёрнуты, о сбое сообщается один раз в консоль.
- Компоненты из файлов `index.vue` больше не называются «index» — берётся имя каталога: `navbar/index.vue` показывается как `navbar`.

## [0.1.0] — 2026-09-16

### Добавлено

- Определение причины перерисовки через `renderTriggered`: проп, реф, ключ стора, индекс массива, значения до и после.
- Диф пропсов между обновлениями с пометкой «новая ссылка, значение то же».
- Оверлей с рамками, цвет которых зависит от частоты перерисовок.
- Панель в shadow DOM: топ по количеству, топ по времени, дерево компонентов, лента событий, фильтр, пауза, сброс.
- Открытие SFC в IDE по клику через дев-сервер.
- Публичный API: `scan()`, `getStats()`, `getEvents()`, `onRender`.
